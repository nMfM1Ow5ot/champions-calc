## A01：プロジェクト構成

事実:
- 構成は MUSE-PROJECT-TREE.md のとおり。実行系は3つに分かれる。(1) Mac 上の reader.swift（画面取得・認識）、(2) Mac 上の serve.py（ローカルサーバ・同期・アップロード）、(3) ブラウザ上の ui.html＋bundle.mjs（計算 UI と推定）。
- エントリーポイント: Mac では start_all.sh（同期→serve.py→reader の統合起動）、または start_ui.sh／run_reader.sh の個別起動。UI は http://localhost:8765/ui.html。
- 設定に相当するもの: data/ 配下の JSON 群（レギュレーション、仕様差分、使用率）、flag_control.json（手動フラグの制御、実行時生成）、プリセットストア（localStorage＋リポジトリの presets.json）、reader.swift／serve.py のソース内スイッチ定数群（A10 参照）。
- バージョン管理は Git ローカルリポジトリではなく、公開 GitHub リポジトリへの Contents API 経由の push と、ui_manifest.json（ファイル別 SHA-256 と rev）による識別で行う。push は push_update.py が唯一の経路で、セキュリティ確認と機能ゲートを内蔵する。

## A02：システムアーキテクチャ

事実:
- 処理フロー: iPad の画面を Mac の QuickTime Player でミラーリング → reader.swift が画面を取り込み Vision OCR と画像照合で観測 → 出来事を Showdown 形式のプロトコル行と人間可読行に変換し、作業ファイル（battle.log／battle_protocol.log、プロジェクト直下）へ蓄積 → 状態を state.json に書き出し → serve.py が配信し、ui.html が 200ms 周期でポーリングして盤面・推定へ反映する。
- モジュール境界: reader と UI の接点は state.json のみ（単方向）。計算と推定はブラウザ内で完結し、serve.py は計算を行わない。serve.py と reader の接点は flag_control.json（UI→serve.py→reader のボタン要求）とファイル配置のみ。
- ログの流れ: 試合終了時に reader が試合フォルダ（logs/battle_<試合キー>/）へアーカイブ → serve.py が暗号化して GitHub の logs_enc/ へアップロード → Muse 側のフックが到着を検知し、復号・検証して logs_received/ に置く。ただし調査時点では自動アップロードは無効化中（A10）。
- 同期・非同期: reader は撮影と認識を分離した直列処理（上限のあるキュー経由）。UI のポーリングと推定はブラウザ上の同期処理。serve.py はスレッドを使う HTTP サーバで、プリセット保存等にロックを持つ。
- 補助チャンネル: PaddleOCR サイドカー（Python）は reader が監督し、生の OCR 証拠を別ファイル（_paddle.jsonl）に記録するのみで、状態判定には一切使わない（証拠専用）。

## A03：既存の型推定アルゴリズム

事実:
- 実装は estimate_engine.mjs（1,812行）。UI から createEstimator(deps) で生成し、deps 経由で core.mjs の計算機能（damageRolls 等）を受け取る二層構造。
- 推定は二系統の併用。(1) ベイズ推定: 候補集合に対して事前確率を与え、ダメージ等の証拠ごとに尤度で事後確率を更新する。(2) 制約交差（inf）: 観測と矛盾する候補を制約で落とす。
- 候補生成: 候補は種族ごとに上限 96 件。事前の混合は、実コーパス由来（VGCPastes の収集セット＋pokedb 使用率セット）を 75%、合成（使用率分布からの生成）を 25% とする混合（estimate_engine.mjs の混合処理で確認）。チーム条件付きの事前（味方チームとの関係で候補の重みを調整）も入っている。
- 証拠の種類: ダメージ（乱数16本との突き合わせによる尤度評価。damageRolls を使用）、行動順（素早さの証拠）、判明した技・特性・持ち物、ひんし順、場の状態。急所の後付け是正（critPatch）など、観測の訂正に追随する再計算の仕組みがある。
- 仮説フラグ: 観測が候補の説明範囲を超えた場合に、こだわりハチマキ／メガネ（過大ダメージ時）、とつげきチョッキ（過小ダメージ時）等の「表示されない効果」を仮説として立てる。表示で判明する効果（きあいのタスキ、半減きのみ等）は仮説対象から除外されている（ユーザーの指摘による是正済み）。
- 順位付けと出力: 事後確率順の候補一覧と、確率で重み付けした代表値（candRanges 等）を UI が表示する。
- 既知の限界（プロジェクト内で認識済み）: 行動順の比較は「隣り合う技のペア」単位でしか行われず、推移的な比較や相手同士の比較は存在しない。候補空間の上限（96件）が天井になる。入力側（認識）で取りこぼした証拠は推定に届かない。改善計画ドラフト（ESTIMATION_IMPROVEMENT_PLAN_DRAFT.md）が未実施で存在する。実力の測定値としては、LOTO 条件のシミュレーションで完全一致 43.0%／三要素一致 91.2% という記録が引き継ぎ資料に残る（本調査では再測定していない）。
- 未確認: 推定の実時間性能の上限（1証拠あたりの処理時間の体系的な測定値）は本調査では確認できなかった。

## A04：データ構造

事実:
- 型（ビルド）の内部表現は spec と呼ばれる辞書で、種族・フォルム（megaSpecies と mega フラグで分離保持）・性格・SP（UI 表示名は努力値）・持ち物・特性・技・現在 HP（割合と実数の併用）を持つ。計算時は core.mjs の toPokemon で @smogon/calc の Pokemon へ変換する。
- 戦闘状態は reader 側では state.json のスキーマ（mine／opps の各個体、oppTeam、oppRevealed、events、field、sideConditions、hazards、battlePhase、flagMode 等）で表され、UI 側はこれを applyState で内部 state へ写す。state.json のトップレベルキーは reader 側で固定の集合として管理されている。
- 登録6体: my_team.json（種族ごとの型一式）。公開側は暗号化した my_team.enc が正本で、平文はローカルのみに置く。
- 個体 ID: 明示的な個体 ID はなく、側＋枠（p1a 等のラベル）と種族名で識別する。試合の識別は開始時刻由来の試合キー（battle_YYYYMMDD_HHMMSS）。
- 観測履歴: reader 内ではプロトコル行の蓄積（battleLog）と表示行（displayLog）が履歴そのもので、推定用イベント列（battleEvents）も併せて保持される。UI 側では推論過程ログ（inference）が対戦別に蓄積・保存される。
- 観測の撤回・訂正への対応: ログ行の引き戻し・差し込み（交代ブロックの再配置、ターン行の後付け挿入等）により蓄積側で順序を修復する。推定側は critPatch のような後付け是正を持つ。一方で、ターミナルへの印刷は1回きりで撤回できないため、実時間表示と最終ログで順序が食い違うことがある（既知の仕様的な帰結として記録されている）。

## A05：画面取得・観測処理

事実:
- 画面取得: reader.swift が QuickTime Player のウィンドウを周期的に取り込む。撮影と認識は分離され、撮影は独立した直列処理で上限のあるキューへ渡す（2026-11-22 の分離以降）。PaddleOCR 併走時の実測で、フレーム処理間隔の中央値は約 0.76 秒（検証試合の記録）。
- 認識の経路は大きく3つ。(1) プレート（名前・HP の表示枠）: 種族と HP の読み取り。交代の確定はこの経路が唯一の本線で、同一種族が2フレーム連続で読めることが確定条件。(2) メッセージ帯: 技・状態変化等の文の読み取り。(3) ゲーム内「ログを見る」画面: 行動履歴の取り込み。
- 見せ合い同定: スプライト特徴量の照合＋タイプアイコンのテンプレート照合（実フレームのサンプル群との最近傍）＋複数回の試行のマージ。色違いタグ付きテンプレートは通常照合から除外される。誤同定した個体は原則としてテンプレート登録する運用（ユーザーの指示）。
- 信頼度管理: 候補スコアとマージン、複数試行の票、確定条件（連続読み回数）で管理する。確定できない観測は証拠としてのみ記録し、状態には反映しない設計（証拠と解釈の分離）。
- 誤認識・欠測への対応: 文字化け救済（辞書照合による段階的な救済順序が形式化されている）、あり得ない行のガード（場の実在と矛盾する特性行・技行を記録しない）、ターン構造ガード（ターン行の後付け挿入、ひんし行の先行排出）。欠測時は既定帰属に頼らず証拠を残す方針へ移行済み（フェーズ3）。
- 順序逆転への対応: A04 の引き戻し機構。ただし2ターン以上遅れた交代の引き戻しや、特性判明によるフォルム訂正の名前書き換えは、印刷済み表示とのずれが残る限界として認識されている。
- 型推定への入力形式: state.json の events（技の使用順、特性の発動順、ダメージ等）と、UI 側の盤面 spec。推定結果自体は state.json に保存されない（推論ログが別ファイルに残る）。

## A06：ダメージ計算器

事実:
- 使用計算器: @smogon/calc（package.json で ^0.12.0。Showdown の公式計算ライブラリ）。core.mjs が Generations／Pokemon／Move／Field／calculate を import して使う。自作の計算式は持たない。
- Champions 適合: IV31／Lv50／EV=SP×8 と置くことで Champions の実数値が完全一致することが検証済み（core.mjs 冒頭の注記および検証記録）。SP は UI 上「努力値」と表示し、1能力 0〜32、合計 66。
- 乱数: damageRolls が calculate の結果から乱数16本を返す。複数ヒット技はヒットごとの16本を要素ごとに合計する。変化技・無効・例外はフラグ付きで返す。
- 端数・補正: ライブラリ側の処理に従う。プロジェクト側の追加は、KO% の表示ロジック（回復を見込む計算、ターンごとの再計算、9HKO 超の補完）と、無効相性でライブラリが例外を投げる場合の事前判定など。
- 仕様変更への対応: data/spec_patches.json の差分レイヤーを gen データへ直接適用し、UI の「仕様」セレクタで切り替える（シーズン M-8 は 2026-12-02 10:59 終了予定として記録）。
- 検証済み事項: 2026-11-21 に calc.pokemonshowdown.com と突き合わせる監査を行い、計算コアに欠陥なし（UI 側の表示欠陥1件のみで修正済み）。tests/calc_audit.mjs が UI 配線と素のライブラリの突き合わせを継続する。
- 未確認事項: UI の表示素早さに天候の素早さ特性やこだわりスカーフを織り込んでいない点が、判断待ち事項として残っている（ユーザー未判断）。

## A07：データベース

事実:
- データソースと取得元: (1) pokedb（champs.pokedb.tokyo）の使用率データ → fetch_usage.mjs が取得・生成（usage_sets.json 等）。(2) VGCPastes Repository の収集セット → fetch_vgcpastes.mjs（744 チーム）。(3) PokéAPI → 日本語名・種族データ等の生成（fetch_names.mjs 等）。(4) Showdown 系データは @smogon/calc の gen データに内包。
- データ範囲の取り決め: champions_dex.json が全 gen9 母集団、regulation.json が Champions 実装範囲のフィルタであり、認識の参照データの出所でもある。
- 更新方法: pokedb は定期ジョブ（毎日 00:00 JST）がキャッシュを消して全件再取得し、検証（件数・シーズン一致）を通して push する。VGCPastes も同じジョブに相乗りする。regulation.json の specialElements は再生成時に保持される（レギュレーション名が変わった場合のみ落とす）。
- 合法性判定: レギュレーションの範囲（種族・持ち物・技）と spec_patches が担う。推定の候補はレギュレーション範囲に限る。
- 未収録データの処理: 使用率に無い種族は usage の既定型で補う経路がある。VGCPastes の一部チーム（MC564、MC528）はペースト自体の欠陥として収録対象外のまま残っている。
- 既知の不具合（調査中に判明している記録）: fetch_usage.mjs の手書き対応表（ITEM_JA2EN）に、実（ベリー）の日英対応の取り違え 15 件・欠落 13 件があったことが 2026-11-24 に判明し、修正された（ローカル未 push。MUSE-SNAPSHOT.md 参照）。生成時に items_ja.json を優先して引く形へ変更済み。

## A10：不具合・技術的負債

事実（プロジェクト内で認識・記録されているもの）:
- 無効化中の仕組み（いずれもスイッチでコードは残置）: ログの自動アップロード（_AUTO_UPLOAD_ENABLED = False）、備考ゲート（_NOTE_GATE_ENABLED = False）、途中終了の控え保存（interruptedSaveEnabled = false）、黒画面待機（blankStandbyEnabled = false）、自チーム暫定リストの UI 適用（MINE_TEAM_PREVIEW_APPLY = false）、terminal 表示限定は有効（limitTerminalOutput = true／_LIMIT_TERMINAL_OUTPUT = True）。
- logs_enc／index.json の肥大化: index.json は 189,156 バイト（2026-11-24 監査実測）で、自動送信の再開後は約38KB/日のペースで Contents API の 1MB 上限へ約3週間で到達する見込み。対策計画（INDEX_BLOAT_PLAN.md）は改訂版まで作成済みで未実施。
- 特性の発動表示文の一覧が存在しない: 特性ごとの発動文への変換は事例ごとの個別対応の積み重ねで、網羅性の確認記録がない。2026-11-23 の試合で、もらいび の文が変換されず特性として反映されない事例が発生した。
- 行動順の証拠の保持が単一スロット: 隣接ペアの材料が次のペアに上書きされ、証拠が使われずに消える場合がある（2026-11-23 に判明）。
- ファイル巻き戻し事故の履歴: serve.py の自己修復がテスト実行時に実プロジェクトへ作用し、未 push の編集が失われた事故が 2026-11-22 に3回発生した。対策（実サーバ時のみ修復、テストでのスタブ化）は当時の記録上は実装途上とされており、本調査では現在の serve.py に当該ガードが入っているかは未確認。
- 対戦中の push が実戦セッションを乱した事例（2026-11-22）があり、以降は対戦中とみられる時間帯の push を避ける運用。
- ui_manifest.json に my_team.json のハッシュが含まれるがリポジトリに本体が無い、というマニフェストと実体の不整合が監査で観察として記録されている（平文の流出ではない）。
- Sticky Web（ねばねばネット）のバックエンド入力経路が未実装（保存側の名称のみ）。
- 推定の改善計画（ESTIMATION_IMPROVEMENT_PLAN_DRAFT.md）と index 対策は計画段階で未実施。

## A11：既存の開発規則

事実:
- AI 向けの規則は、プロジェクト横断のものとプロジェクト固有のものがある。固有のもの: IMPLEMENTATION_MANUAL.md（実装の手順。十分な計画と自己議論、管轄の固定、完了条件、証拠優先、ゲート、push 後の実 rev 検証）、PLANNING_MANUAL.md（議論から指示発出までの流れ。明示指示があるまで発出しない）、SPEC_PATCHES.md（仕様差分の運用）。
- 運用規則（記録から確認できるもの）: ファイルごとの管轄チャットの分担と同時編集の禁止（edit_lock.py による claim／release）、push は push_update.py 経由のみでゲートを迂回しない、reader.swift 変更時は check_reader.sh を必ず通す、core.mjs 変更時は bundle.mjs を再構築する、対戦中とみられる時間帯の push 回避、ZIP の内部フォルダ名の規則。

## A14：UI・出力

事実:
- UI は Showdown の Calcdex を忠実に再現した 1対1（ダブルス盤面）形式で、日本語表示。両軍のパネル、場の状態、サイドコンディション、設置技等を扱う。

## 変更耐性（主要モジュール）

### core.mjs（計算コア）
- 依存: @smogon/calc のみに強く依存。プロジェクト内では ui.html（bundle 経由）と estimate_engine.mjs が利用。
- 契約: spec 辞書の形式と、calcMatchup／damageRolls／statTable 等の export が入出力契約。UI は bundle.mjs 経由でのみ触れるため、core.mjs の変更時はバンドル再構築が必須（怠ると UI が旧ロジックのままになる既知の落とし穴）。
- 置換・再利用: ライブラリ差し替えは calculate の呼び出し箇所に局所化されているが、spec 形式と KO% の表示ロジックはプロジェクト固有で、再利用には切り出しが必要。
- 推定の独立化への影響: 推定は damageRolls と statTable 等に依存するため、推定だけを独立させる場合は core.mjs の該当 export が最小の同梱単位になる。

### estimate_engine.mjs（型推定）
- 依存: core.mjs の計算機能（deps 注入）、候補コーパスのデータ（data/ の meta_sets、vgc_pastes 由来、usage_sets）。
- 契約: createEstimator(deps) と、UI が渡す観測イベントの形式、候補・確率の出力形式。
- 置換・再利用: deps 注入の形になっているため、計算コアの差し替えや、ブラウザ外（node ハーネス）での実行は既に行われている（評価スイートが node で動く）。一方、観測イベントの生成は UI／reader 側の形式に依存しており、独立化の障害は「入力形式の切り分け」に寄る。
- 強く依存している箇所: コーパスのデータ形式（セットの表現）と、core.mjs の spec 形式。

### reader.swift（画面取得・認識）
- 依存: Apple の Vision／AppKit 等（Mac 専用）、data/ の参照データ（species_types、preview_features、type_icons 等）、state.json のスキーマ、flag_control.json の契約。
- 契約: state.json の形式と、ログファイル一式の形式（プロトコル／可読／証拠ファイル）が外部契約。下流（UI、ログ分析、フック）はこの形式に依存する。
- 置換・再利用: 単一ファイル 12,558 行で、撮影・認識・ログ構築・状態管理が同居する。撮影と認識の分離は内部構造として実施済みだが、ファイル単位の分割はされていない。Mac 専用 API への依存が強く、他環境への移植性は低い。
- 強く依存している箇所: 画面レイアウトの前提（プレート位置、メッセージ帯の位置）と Vision の挙動。ゲーム側の画面仕様変更の影響を直接受ける。

### serve.py（サーバ・同期・アップロード）
- 依存: GitHub Contents API、openssl（暗号化）、sync_ui.py、flag_control.json／state.json のファイル配置。
- 契約: HTTP のエンドポイント群（/battle_flag、/calclog、/presets 等）と、logs_enc の配置・index.json の形式が、Muse 側フックとの外部契約。
- 置換・再利用: 標準ライブラリ中心で単体テストが厚い一方、自己修復のような暗黙の副作用を持つ経路があり、置換時はその棚卸しが必要（A10）。
- 強く依存している箇所: index.json の維持方式（丸ごと GET/PUT）が Contents API の 1MB 上限と結びついている（対策計画あり）。

### ui.html（計算 UI）
- 依存: bundle.mjs、state.json のスキーマ、プリセットストアの形式（localStorage＋presets.json）、serve.py のエンドポイント。
- 契約: state.json の読み取り形式と、POST 系エンドポイントの要求形式。
- 置換・再利用: 単一ファイル 4,428 行に表示と状態管理と推定連携が同居する。計算自体は bundle 側にあるため、表示の置換は相対的に容易だが、盤面状態の管理は UI 内に閉じている。

### データ生成群（fetch_*.mjs）
- 依存: 取得元（pokedb、VGCPastes、PokéAPI）の形式変更の影響を直接受ける。手書き対応表のような人手の辞書が残る箇所があり、誤りの混入経路になっている（A07 のベリー対応の事例）。
- 契約: 生成される data/*.json のスキーマが、認識・計算・推定の共通契約。
