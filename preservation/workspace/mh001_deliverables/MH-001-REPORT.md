# MH-001-REPORT — 統合実装報告書

- 対象: 複数ヒット技におけるダメージ乱数分布の計算処理の修正（緊急修正指示書 MH-001）
- 基準点: S001（公開リビジョン 20261124_0418）
- 実施体制: 総合（調査・調整・取りまとめ）、ダメージ計算チャット（core.mjs／ui.html／bundle.mjs）、型推定エンジンチャット（estimate_engine.mjs）。本件は複数の管轄にまたがる作業として、各指示にその旨を明記して実施した
- 実施期間: 2026-11-24 10:42（指示）〜 11:01（最終 push）。検証と本報告書の作成はその後

## 1. 指摘された欠陥の実在確認

欠陥は実在した。S001 以降、対象ファイルに変更は無く（ハッシュで確認）、以下の2箇所に同じ添字同士の加算が存在した。

1. core.mjs の damageRolls：ヒット数（moveSpec）が指定された場合に、ヒットごとの16本を要素ごとに合計して「合計ダメージの16本」として返していた。
2. core.mjs の calcDirection 内 rollsOf：複数ヒット技すべてについて、表示用の16本を同じ方法で作っていた。

加えて、ヒット数指定が無い複数ヒット技では damageRolls がライブラリの入れ子配列をそのまま rolls として返しており、数値を前提とする利用側で件数が無言で0になる（または NaN になる）経路があった。

## 2. 根本原因

@smogon/calc の calculate は、複数ヒット技について「ヒットごとの16本の配列の配列」（各行＝そのヒットの周辺分布）を返す。この入れ子を単一の16本へ潰す際に、各ヒットの乱数が独立であるにもかかわらず、同じ添字同士（＝全ヒットが同じ乱数値を取る完全な正の相関）を仮定して加算していたことが原因である。最小値・最大値・平均は正しい分布と偶然一致するため、欠陥が表面化しにくい構造だった。詳細は MH-001-MATH.md。

## 3. 影響を受けていた機能

- 型推定のダメージ尤度（ベイズ両方向と仮説フラグ再計算）：誤った分布に基づく件数比が尤度になっていた。真の候補だけが0件になる場合、最小値（BAYES_FLOOR）のみが掛かり、実質的な誤排除（軟らかい排除）が起こり得た。
- 型推定の制約交差（inf）：到達可能集合が誤っており、真の（性格, SP）の組合せを到達不能として落とす硬い誤排除があり得た。
- 推定表示（candRanges）：KO% が誤った分布の割合だった（平均は偶然正しい値だった）。ヒット数指定が無い場合は平均も NaN で壊れていた。
- 計算 UI のバルーン表示：複数ヒット技で、到達し得ない合計値を含む16本が表示されていた（最小〜最大と KO テキストは正しかった）。
- ただし重大な限定がある。調査の過程で、推定エンジンの入口に複数ヒット技を対象外とするゲートがあることが判明した。主要な複数ヒット技18種の実測で、現行の本番経路では複数ヒット技のダメージ証拠は inf／ベイズのいずれにも届いておらず、上記の推定側の誤判定は潜在的なものだった。実際に誤っていたのは推定表示（candRanges）とバルーン表示である。このゲートの扱いはユーザーの判断（「ゲートも解除して推定に取り込む」）により、本修正で解除した（§10 参照）。

## 4. 確認したゲーム仕様と根拠

- 確認済み（本家シリーズの文書化された仕様）：各ヒットのダメージ乱数は独立に生成される（16段階、0.85〜1.00、等確率）。急所判定もヒットごとに行われる。2〜5回技のヒット数分布は 2回 37.5%／3回 37.5%／4回 12.5%／5回 12.5%（スキルリンクでは最大回数、サイコロ（Loaded Dice）では4〜5回）。トリプルアクセル等はヒットごとに命中判定があり、外れると終了する。根拠は Bulbapedia のダメージ計算の研究記録等の公開資料。
- ライブラリの実装で確認した仕様：@smogon/calc 0.12.0 の calculate は、ヒットごとの周辺分布を返し、ヒット間で決定的に変化する要素（キーのみ／マランのみのランク変化、メトロノーム等）は checkMultihitBoost で行ごとに織り込む。ヒット数の既定は、固定数はその数、2〜5回技はスキルリンク時5・それ以外は3、multiaccuracy 技は指定値またはその数である。
- 未確認：Pokémon Champions 固有の公式な仕様確認は得られていない。本修正の独立乱数モデルは、本家シリーズの仕様に基づく仮定として扱う（§11）。

## 5. 採用した数学的モデル

各ヒットのダメージを独立な確率変数とし、合計ダメージの分布を、各ヒットの周辺分布の離散畳み込みで求めるモデルを採用した。ヒット数は、計算に用いた回数（UI の指定値、または指定が無い場合はライブラリ既定値）に条件付けた分布とし、その前提を推論ログに記録する（assumedHits）。ヒット数自体の分布（37.5% 等）を混ぜる変更は、MH-001 の範囲（他の尤度モデルを変更しない）を超えるため行っていない。

## 6. 修正したアルゴリズム

- core.mjs に純関数 convolveHitRolls を新設：整数の組合せ数を保持する Map による動的計画法の畳み込み。16^n の全展開はしない。
- core.mjs に damageDistribution を新設：calculate の結果から分布 { values, counts, total } と min／max／hits／multi を返す。
- damageRolls は複数ヒットで { rolls: null, dist, hits, multi: true } を返すよう変更し、偽の16本を作らない。
- calcDirection の rollsOf を廃止し、複数ヒットでは行に dist を載せる形に置換。
- estimate_engine.mjs の全利用箇所（ベイズ両方向、仮説フラグ再計算、inf、candRanges）を、分布の確率質量に基づく計算に置換。ベイズへは質量×16 を渡し、単発では従来と算術が一致する形にした。
- 推定エンジンのゲートから multihit 項を解除（ユーザーの判断による）。

## 7. 修正後のデータ構造

分布は { values: 昇順のダメージ値の配列, counts: 各値の整数の組合せ数, total: 総組合せ数 } で表す。確率は counts/total。最小・最大は values の両端。計算の前提（ヒット数と、その出所）は hits と、推定側では trig の assumedHits に記録される。対応外・計算不能は、damageDistribution の { status } / { immune } / { error } の区別で識別でき、分布が得られない証拠は推定側で保留される。

## 8. 既存処理との互換性

- 単発技：数値結果は従来と完全一致する。固定場面（実数観測＋割合観測）の事後分布と trig のハッシュが修正前後で完全一致したことで検収した（ハッシュは MH-001-TEST-REPORT.md）。
- 変化技・無効・例外時の戻り値の形は不変。無効は推定側で「値0に質量1」の退化分布として従来の rolls:[0] と同じ挙動を再現する。
- 元々正しかった経路（core.mjs の damageDist＋convolveDist による回復込み KO 計算、ライブラリの kochance）には触れていない。
- UI の min／max／KO テキストは不変。バルーンは複数ヒット時に分布表示へ変わった。

## 9. 修正前後の具体的な比較

模式例（各ヒット [10, 11, 12, 13]、2ヒット）：
- 修正前：[20, 22, 24, 26] の4値だけが、各25%として扱われた。21、23、25 は到達不能と判定され、観測23は尤度0になった。
- 修正後：20:6.25%、21:12.5%、22:18.75%、23:25%、24:18.75%、25:12.5%、26:6.25% の正しい分布。観測23の尤度は25%。

実例の検証（トリプルアクセル、タネマシンガン、ダブルキック、ポピュレーションボム）はいずれも全列挙の参照計算と一致した（MH-001-TEST-REPORT.md の T09）。

## 10. 実装担当が独自に行った設計判断と理由

- 総合：分布の受け渡し契約（§7 の形）を管轄間で固定した。理由は、core 側と推定側の解釈のずれを防ぐため。
- 総合：ゲート解除の可否はユーザーの判断に委ねた。理由は、数学の修正を超えて推定の挙動を変える変更であり、MH-001 の文面だけでは範囲が確定しなかったため。ユーザーの判断は「ゲートも解除して推定に取り込む」。
- 型推定側：bayesApply へ質量×16 を渡す形にした。理由は、単発で従来の算術（件数/16）とビット単位で一致させ、既存の保存形式と公開契約を変えないため。
- 型推定側：under 判定（とつげきチョッキ仮説側）で、計算例外の候補の扱いを従来の「矛盾しない側」から「分布が得られないため不成立」に揃えた。委任の「分布が得られない場合は保留」の指示に沿う保守側の扱いであり、開示のうえ実施した。over 判定側は従来と完全等価。
- 総合：bayes_equiv の golden は再記録しないと判断した。差分は本修正に由来しない既存のドリフト（M-8 データ更新等）であることが、エンジンを修正前に差し替えても同一差分になることで確認されており、再記録は MH-001 の範囲外のデータ保守にあたるため。

## 11. 未確認仕様・対応外のケース

- Champions 固有の乱数独立性：公式確認なし。本家シリーズの仕様に基づく仮定として計算している。
- ヒットごとの急所の独立判定：ライブラリの出力は全ヒット共通の急所フラグしか表現できないため、一部のヒットだけが急所だった観測は正しく表せない。対応外。
- ヒットごとの命中判定と途中終了（トリプルアクセルの外れ、ポピュレーションボムの各ヒット命中判定、相手のひんしによる終了）：ライブラリの周辺分布に表れないため対応外。合計分布は「全ヒットが命中し、相手が倒れていない」前提の条件付き分布である。
- 結果依存の状態変化（HP 割合で発動する持ち物等、前のヒットの結果で後のヒットの分布が変わるもの）：ライブラリが織り込むのはヒット回数で決定的に決まる変化のみであり、結果依存のものは対応外。
- 可変ヒット数の分布混合：行っていない（§5）。

## 12. 残存するリスク

- 独立性の仮定が Champions 実機と異なる場合、分布の形が実機とずれる可能性がある。実戦ログでの検証（複数ヒット技の観測ダメージが分布の支持集合に収まること、尤度が極端に偏らないこと）が次の確認手段である。
- ゲート解除により、複数ヒット技の証拠が新たに推定へ効くようになった。想定ヒット数（assumedHits）が実ヒット数と異なる観測では、条件付けのずれが尤度に残る。
- ライブラリの kochance は 16本×4ヒット以上で間引き近似を行う（approx. 表示）。本修正の対象外として残る。

## 14. 総合的な修正状況

MH-001 の完了条件について：同じ添字同士の加算による分布生成は2箇所とも解消され、対応対象については数学的に正しい分布が得られ、推定の尤度・候補排除・表示は修正後の分布と整合した。単発技と既存機能に回帰は無い（全スイート PASS と単発不変のハッシュ検収）。未確認仕様については、仮定の明示と、分布が得られない場合の保留という安全な処理が行われている。

ただし §11 のとおり、Champions 実機の仕様への適合性は未検証であり、独立監査担当AIによる独立監査を経るまでは、最終的な品質保証が完了したとは判断しない。対応済みの範囲は「独立乱数モデルの下での分布計算とその全利用箇所への接続」であり、未承認の範囲は「実機仕様への適合」と「§11 の対応外ケース」である。
