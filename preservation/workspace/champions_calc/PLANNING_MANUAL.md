# 計画・指示マニュアル（議論から実装指示までの流れ）

- 目的：大きな変更について、議論と計画の段階で判断を済ませ、実装指示を「実装者が迷わない形」で出すための手順を定める
- 位置づけ：実装そのものの進め方は IMPLEMENTATION_MANUAL.md が担い、本マニュアルはその上流（前提の確定から指示の発出まで）を担う。両方をあわせて使う
- 適用範囲：管轄をまたぐ実装、並行処理や実機確認を伴う変更など、計画の質が結果を左右する案件。小規模で可逆な修正にまでこの流れを適用すると過剰になるため、案件の重さに応じて省略してよい

## 全体の流れ

1. 前提の確定
2. たたき台の作成
3. 重要度の選定（前段階の自己議論）
4. 自己議論（複数ラウンド）
5. 改訂版の確定
6. 監査指示と報告計画の具体化
7. 明示指示による発出

## 1. 前提の確定

- すでに決まっていること（ユーザーの決定、過去の経緯）と、まだ決まっていないことを切り分けて書き出す
- 管轄を確認する（主担当、相談先、監視役の候補）。管轄が曖昧なまま計画を進めない
- 現状を実物で確認する（edit_lock の宣言状況、関連ファイル、既存の仕組みの実コード）。思い込みで前提を置かない
- 引き継ぎや経緯がある場合は、出所を明示して受け取る

## 2. たたき台の作成

- 次の項目を含める：目的、前提（決定済み事項）、固定事項の候補、分担、ステップと各ステップの完了条件、ユーザーの作業、見積もり、範囲外
- 見積もりは「設計判断の時間」と「実装の時間」を分けて書く。暦の見積もりには、ユーザーがいつ対応できるかという前提を明記する
- 順序に意味がある場合は、その順序自体を固定事項の候補にする（例：実機確認が終わるまで push しない）
- たたき台は提示までとし、この段階ではいかなる管轄にも指示を出さない

## 3. 重要度の選定（前段階の自己議論）

- 本段階の自己議論に入る前に、何が重要かを決めること自体を自己議論の対象にする。重要度の初期案をそのまま採用しない
- 賛成・反対の2つの立場ではなく、複数の立場から各論点を眺めて順位を付ける。立場の例：
  - 壊れたときの影響：失敗した場合に何が失われるか、元に戻せるか
  - 起きやすさ：発生する見込みがどれだけあるか
  - 検証可能性：後から実物で確かめられるか。確かめられないものほど、先に詰める価値が高い
  - 波及：他の論点や他の管轄、後の工程へどれだけ影響するか
  - ユーザーの巻き込み：ユーザーの作業や判断が必要になるか、その負担と時機は適切か
  - 先送りのコスト：後から決め直す場合の手戻りの大きさ
- ある立場では小さく見える論点が、別の立場では致命的になることがある（例：記録時点での証拠の加工は、速度の立場では些細でも、検証可能性の立場では証拠そのものを壊す）。立場によって評価が割れた論点は、その割れ方自体を記録する
- この段階の成果物は、重要度順の論点リストと、順位付けに使った立場と理由である。本段階の自己議論はこの順序で行う

## 4. 自己議論

- 論点の並びは、前段階で選定した重要度順とする。各論点で賛成側と反対側の両方を検討し、結論を出す
- 結論で案が変わった場合は、変更前の案と変更の理由を残す。変わらなかった論点も、維持の結論として残す
- 1ラウンドで終わらせず、「さらに論点がないか」を繰り返し検討する。論点が計画レベルで出尽くしたら、その旨を正直に述べ、それ以上は無理に作らない
- 数値ありきの細部（実測しないと決められない値）は、ここで決め切らず、実測を行うステップへ判断の物差しだけを渡す（例：「速さと読みの質の見本で決める」）
- ユーザーの判断が計画に織り込まれるべき点（許容できる遅延、保険を残すかどうか等）は、自己議論の中で論点として表面化させる

## 5. 改訂版の確定

- 自己議論の全結論を反映した改訂版を作り、旧版は改訂版に置き換える
- 実装者が迷う余地（数値の決め方、前提の解釈、例外の範囲）が残っていないかを通読で確認する
- 固定事項は、後から第三者がコードや実物と照合できる形（列挙できる形）で書く

## 6. 監査指示と報告計画の具体化

- 監査指示には次を含める：開始点（指示が全管轄に到達した時点）、実行間隔、初回の扱い、開始遅滞と停滞の判定基準、照合項目、逸脱の格付け（違反／リスク／観察）、権限の限界（読み取り専用、差し止めはしない）、終了条件
- ユーザーの作業待ちになり得るステップがある場合は、「待ちである旨の報告が出ていれば停滞としない。沈黙だけを停滞とする」という例外を基準に含める
- 小報告（節目ごとの報告）を先に決める：着手報告、ステップ完了ごとの報告、待ち状態に入った時点の明示報告、異常に気づいた時点の即時報告。それぞれ送り先と担当を明記する
- 大報告（完了時の総合報告）の構成を先に決める：実施内容と固定事項への適合、実測値、計画時点の想定と実際の比較（所要時間と暦、効果、ユーザーの作業時間、論点で挙げたリスクの的中）、それに基づく考察と結論（守る価値が実証された固定事項、次回から変えるもの、次の計画への判断材料）、知見化と全体への共有
- 知見化の保存先を先に決める：プロジェクトの事実は MEMORY.md、運用の約束事は AGENTS.md、実装方法の教訓は IMPLEMENTATION_MANUAL.md への反映案として大報告に含める。監査の終了確認では、知見化が実際に行われたかも照合する

## 7. 明示指示による発出

- 発出は、ユーザーの明示指示（「指示を出して」「実装して」等）があるまで行わない。意味の確認、計画の提示、方針への同意は、発出の指示ではない
- 各指示には次を含める：委任であることと出所、複数管轄にまたがる場合はその旨と他の管轄名、前提と固定事項、ステップと完了条件、報告計画、管轄固有の約束事（edit_lock、ゲート、対戦中の push 回避等）
- 相談だけを担当する管轄には、ファイル編集をしないことと、相談の範囲を明記する
- 発出側のチャットが担う調整作業（自側の基盤の対応など）は、指示とあわせて自ら済ませる
- 発出後は、全体の分担を簡潔にユーザーへ報告する

## 横断の約束事

- 判断や決定をユーザーに求める場面では、選択肢ボタンを出す
- 時刻や期限の判断は、推定ではなく実時計で確認する
- 進捗は部分ごとに速やかに報告し、完了は明示する。他チャットからの連絡を中継するときは、出所を冒頭で明らかにし、三人称の説明文で書く
- push の完了報告は既存のルールどおり（実施側は連絡・進捗管理へ通知し、報告は同チャットから、1回の push につき1メッセージ）
