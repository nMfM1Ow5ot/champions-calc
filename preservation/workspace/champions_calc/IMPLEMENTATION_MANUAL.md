- 実装マニュアル（champions_calc の実装指示・実実装を行う際は、毎回このファイルを参照すること）
- 目的は、判断を先に済ませて実装中の迷いと手戻りをなくすこと
- 十分な計画とAIによる自己議論
  - 実装前に計画を立て、目的・構成・手順・完了条件を確定事項として書き出すこと
  - 計画はAIによる自己議論で磨くこと（論点は複数挙げ、重要度順に並べ、各論点で賛成側と反対側の両方を検討し、結論を計画へ反映すること）
  - 自己議論で案が変わった場合は、変わる前の案と変更の理由も残すこと
  - 実装者が迷う余地（数値の決め方、前提の解釈、例外の範囲）は、自己議論と相談で着手前に潰すこと
- 分担と管轄の確定
  - 主担当・相談先・監視役を着手前に決めること
  - 管轄をまたぐ場合は、その旨と全体の分担を、指示と報告の両方に明記すること
  - 専門的な判断（認識精度、計算仕様、推定の扱いなど）は、担当管轄へ相談し、回答を得てから確定すること
- 境界と前提の確定
  - 共有してよい範囲と触れてはいけない範囲を先に限定すること（共有は必要最小限にすること）
  - 前提が2通りに解釈できる箇所は、例外を列挙する方式で先に確定すること（例：実時間のままにする対象の列挙）
  - 部分的な移行や中途半端な適用は、異なる前提の混在でかえって悪化するため避け、系統ごとに一括で揃えること
- 手順と完了条件
  - 作業をステップに分け、各ステップの完了条件を着手前に決めること
  - 順序に意味がある場合は、その順序自体を確定事項にすること（例：実機確認が終わるまで push しない）
  - 開始報告と節目ごとの進捗報告を行い、完了は明示すること
- 証拠と検証可能性
  - 後から検証できるよう、観測と判断の根拠を記録として残す設計にすること（捨てる情報についても、証拠として残す方法を検討すること）
  - 変更前後を同じ条件で比較できる物差し（ハーネス、評価、実測値）を用意してから着手すること
  - 出荷と実戦での検証完了は分けて扱い、未検証のまま完了としないこと
- 並行作業の安全
  - 共有ファイルは edit_lock で同時編集を防ぎ、他チャットの編集が終わるまで着手しないこと
  - 対戦中とみられる時間帯の push は避けること
  - 机上の検査で担保できない種類の変更（並行処理、タイミング依存）は、実機確認を必須とすること
- ゲートと push
  - 型チェック・ハーネス・テスト・セキュリティの各ゲートをすべて通過してから push すること（ゲートは迂回しないこと）
  - push 後はリポジトリの実 rev と内容の一致を検証すること（完了報告だけで完了としないこと）
  - push の完了は、連絡・進捗管理チャットへ一文で知らせること
- 監査と振り返り
  - 大きな変更には期間限定の監視監査を付け、開始遅滞・停滞の判定基準と、時刻は実時計で確認することを先に決めること
  - 完了後は、想定（所要時間・効果）と実際の比較を行い、得た知見を蓄積して次の計画に活かすこと
