# logs_enc/index.json 肥大化対策 計画（改訂版）

状態: 保留（2026年11月24日、ユーザーの指示）。改訂版は総合へ報告済み。実装はユーザーの別途明示指示があるまで行わない。
進め方: PLANNING_MANUAL.md（前提の確定→たたき台→重要度の選定→自己議論→改訂版→監査指示と報告計画の具体化）。
主担当: バックエンド。相談先: ログ分析チャット（過去ログ取得の要件）。
実測の出所: 監査の 2026年11月24日 00時回。

## 目的

- logs_enc/index.json が Contents API の 1MB 上限に達して、ログ送信（serve.py の index 維持）と到着検知（フックの index 取得）の双方が壊れる事態を、構造的に防ぐ。
- あわせて、logs_enc 本体の肥大（983 ファイル／約385MB）についても、対処の段階と発動条件を決めておく。

## 前提

### 決定済み（ユーザーの決定・固定の制約・実測）

- index.json は 189,156 バイト（983 エントリ、1 件は {name, sha256, uploaded_at} で約190バイト）。
- 自動送信の再開後は約38KB/日（約200 エントリ/日）のペースで増え、1MB まで約3週間（監査実測）。
- 現在は自動送信が無効（_AUTO_UPLOAD_ENABLED = False）のため、index の成長は止まっている。再開の時期は未定で、ペースは再開後に再実測する。
- 過去の試合ログがログ分析で取得できる状態を維持する（アーカイブする場合、その取得経路も計画に含める）。
- 送信済み記録による二重送信防止を後退させない（sent_battles.json は Mac ローカルの試合キー基準で、index の形に依存しない。アップロード再開時の index マージ修理も同じ意味を保つ）。
- 暗号化と team_key の扱いは現行から変えない。
- serve.py は index をアップロードのたびに Contents API で丸ごと GET/PUT している。フック（champions-log-watch）は Contents API で index.json を取得し、新着を検出している。どちらも 1MB が天井になる。

### 未決定（計画の中で判断材料を示し、実装指示の前にユーザーの判断を仰ぐ点）

- 別リポジトリ化（第2段階）の要否そのものと、作る場合のリポジトリ名・公開範囲。
- 非常に古いログをリポジトリから削除するか（本計画では削除しないを既定とし、判断は先送り）。
- 自動送信の再開時期（本計画の前提変数。再開が決まった時点でペースを再実測し、段階の期限を再計算する）。

### ログ分析チャットへの相談結果（2026年11月24日 回答）

- 再分析は原則として手元の logs_received のコピーで完結する。リポジトリからの再取得は、到着経路が失敗した例外ケースのみで、全試合のうち数件程度。目的は「ローカルに無い・不完全なファイルの補完」。
- 再取得の対象はいずれも当日の直近の試合（数日以内）。数週間・数か月前の試合を取り直した実績はない。古い試合についてリポジトリは「ローカルが失われた場合の復旧元」という位置づけ。
- 使いやすい形: 試合キーから所在を引ける一覧があること。エントリ形式 {name, sha256, uploaded_at} がアーカイブ側でも維持されること（特に sha256 は照合に必須）。ファイル名と暗号化形式が変わらないこと。取得は現行の gh.py 経由の API 手続きをキー指定でそのまま使えること。
- 困る形: 所在一覧が無くエントリだけが消える形、sha256 が落ちる形、異なる認証・経路が必要になる形、再暗号化や改名を伴う形。
- 到着検知は加算型（新規ファイル名の出現だけを検知）で、過去エントリが現行 index から消えても誤検知は増えない。
- 実務上の注意: 到着直後のファイルは、サーバ側で追記中の間 SHA 照合に失敗して再試行集合に戻る運用があり、その間は当該エントリが現行 index に残っている必要がある。直近数日分のエントリが現行 index に残る形であれば問題ない。

## 固定事項の候補（第三者が照合できる列挙形）

1. ホットな index（logs_enc/index.json）は、名前と形式（{files: [{name, sha256, uploaded_at}]}）を変えず、フックは無変更で動き続ける。
2. ホット index のサイズには上限を設け、上限超過時は古いエントリから閉じたアーカイブ片（シャード）へ移す。上限とシャードの閉じ方は「サイズ基準」で決める（時間基準は従）。ただし安全窓として、直近の一定期間（目安 7 日）のエントリはサイズ上限より優先してホット index に残す（到着直後の SHA 照合の再試行が当該エントリを現行 index に必要とするため。ログ分析チャットの指摘）。上限と安全窓が競合する場合は安全窓を優先し、その状態は閾値アラートで検出する。
9. シャード側でもエントリ形式 {name, sha256, uploaded_at} を維持し、ファイル名と暗号化形式は変えない。取得は現行の gh.py 経由の手続きをキー指定でそのまま使える形にする（ログ分析チャットの要件）。
3. シャードは一度閉じたら不変（書き換えない）。作成順は「シャード本体→所在一覧→ホット index」の順とし、中断しても再実行で同じ結果になる（冪等）移行にする。
4. 所在一覧（logs_enc/shards.json）は、シャード名と、そのシャードが担うエントリの範囲（試合キーの範囲と件数）を保持する小さなファイルとし、増加はシャード 1 件につき 1 行程度に抑える。
5. どのシャードにも記録されたファイルは「送信済み」とみなす意味を変えない。アップロード再開時のマージ修理は、ホット index と所在一覧＋シャードを合わせた全体を正とする。
6. ファイル本体（logs_enc/*.enc）の配置と暗号化は第1段階では変えない。
7. 閾値アラートを併設する: ホット index が想定上限を大きく超えた場合（＝ロールオフ不全の信号）と、logs_enc 総量が第2段階の発動値を超えた場合に、総合へ報告する。
8. 実装は serve.py とテストが中心で、reader.swift と UI には触れない。フック側の取得スクリプトは、過去分のオンデマンド取得に対応する場合のみ最小限の追加を行う。

## ステップと各完了条件

### 第0ステップ: 実測とパラメータ確定
- 自動送信の再開見通しに合わせ、index の増加ペースを再実測する（再開前なら現行実測 38KB/日を仮置き）。
- 物差し: シャード 1 件は、実測ペースで 500KB を超えないこと。ホット index の上限は 400KB を目安とし、ペース実測で裏付ける。
- 完了条件: パラメータ（上限値、シャードを閉じる条件）が数値で確定し、計画の追記として残る。

### 第1ステップ: 既存エントリの移行（シャード化）
- 既存 983 エントリを uploaded_at の古い順にシャードへ切り出し、所在一覧を作り、ホット index には直近分だけを残す。
- 移行は serve.py の起動時移行の前例（フォルダ移行と同じく、既存を壊さず、再実行可能）として実装する。移行中は自動送信が無効であることを前提にし、移行の完了までは再開しない。
- 完了条件: リポジトリ上で、所在一覧＋全シャードのエントリ合計が移行前の 983 件と一致すること。フックのドライランで新着検知が従来どおり動くこと。任意の古い試合 1 件について、所在一覧→シャード→ファイル本体の経路で取得できること。

### 第2ステップ: 定常運用のロジック（ロールオフとマージ）
- 新規エントリはホット index へ追加し、上限超過時に古い分を新しいシャードへ移して所在一覧へ追記する。
- アップロード再開時のマージ修理が、シャード分を含めて「送信済み」を正しく判定するよう更新する。
- 完了条件: 新規テスト（ロールオフ、所在一覧の追記、マージ修理のシャード対応、二重送信が起きないこと）が全て合格し、既存のアップロード系テストの結果が後退しないこと（既知の test_upload_resume の 2 件の失敗は従来どおりであること）。

### 第3ステップ: 過去分の取得経路
- フック側の取得スクリプトに、試合キーから所在一覧とシャードを引いて取得する経路を追加する（到着検知の経路は無変更）。
- 完了条件: ログ分析チャットが、古い試合 1 件と直近の試合 1 件の双方で取得を確認すること。あわせて、安全窓内のエントリがロールオフで現行 index から消えていないことを確認すること。

### 第4ステップ: 閾値アラート
- ホット index の異常肥大と、logs_enc 総量の発動値を、定期確認（watchdog の報告経路）で総合へ報告する仕組みを入れる。
- 完了条件: 閾値を人工的に超えた状態で、報告が総合へ届くことを確認すること。

### 第2段階（発動条件つき、今回は設計の枠だけ）
- 発動条件: logs_enc 総量が 700MB を超えた時点、または監査が新たな実測で前倒しを勧告した時点。
- 内容: 古い logs_enc を別リポジトリへ移す。所在一覧にシャードごとの所在リポジトリを持たせる設計（第1段階で先行して入れる）により、移行はファイルの移動と所在一覧の更新だけで済み、エントリの書き換えは不要にする。
- ユーザー判断: リポジトリ名・公開範囲は発動時に仰ぐ。

## 見積もり

- 設計判断の時間: 本計画でほぼ済んでいる。残りは第0ステップのパラメータ確定（実測待ちの分）で、1時間程度。
- 実装の時間: 第1〜第4ステップで、エージェント作業として半日〜1日（テスト更新を含む）。移行そのものの実行は自動で数分〜数十分。
- ユーザーの作業: 計画の承認と未決定事項の判断（15分程度）。Mac 側の手作業は見込まない（serve.py は同期で届き、移行はサーバ側で完結する）。ただし移行の実行中は対戦を控えてもらう前提で、実行のタイミングはユーザーの都合に合わせる。
- 暦の前提: ユーザーが計画承認と移行タイミングの指定に対応できること。自動送信の再開が先に決まった場合は、再開から約3週間という期限が全体の上限になる。

## 重要度の選定（前段階の自己議論）

立場: 壊れたときの影響／起きやすさ／検証可能性／波及／ユーザーの巻き込み／先送りのコスト。
この順で論点を並べた（重要度順）:

1. 移行と定常運用での二重送信防止の不変性（影響: 再送は repo と到着報告を氾濫させる。検証可能性: テストで固定できる）
2. ホット index の上限の保証方法（影響: 本丸の期限。起きやすさ: ペース変動で時間基準は外れる）
3. 過去ログ取得経路の維持（固定の制約。波及: ログ分析の運用全体）
4. 移行の原子性と冪等性（検証可能性: 中断状態は後から確かめにくいので先に詰める）
5. リポジトリ総量（385MB）の扱い（先送りのコスト: 1GB までの余裕は index より長い）
6. Git Data API への移行の採否（前回監査の勧告）
7. 閾値アラートの設計（保険。安価だが単体では解決にならない）
8. エントリの削減（uploaded_at の省略など）（効果が小さい）

## 自己議論の結論（論点ごと）

1. 二重送信防止: 「シャードに記録されたファイルも送信済み」という意味を固定事項 5 として明文化し、マージ修理の正を全体（ホット＋所在一覧＋シャード）に広げる。sent_battles.json 自体は無変更（試合キー基準で index の形に依存しないため、後退の余地はマージ修理側にだけある）。変更なし（当初案を維持）。
2. 上限の保証: 当初案は「直近14日のローリング」だったが、ペースが変われば 14 日分が 1MB を超え得るため、サイズ基準の上限（400KB 目安）に変更した。時間は従の目安に留める。
3. 取得経路: 相談結果を受けて確定した。再取得の実態は「当日の直近分・例外時のみ」であり、日常の再分析は手元コピーで完結する。したがって取得経路は、直近分は現行 index（無変更）、過去分は所在一覧→シャード→本体のオンデマンド取得で足りる。エントリ形式と sha256 の維持、ファイル名と暗号化の不変を固定事項 9 に追加した。あわせて、到着直後の再試行が現行 index にエントリを必要とする点が判明し、安全窓を固定事項 2 に追加した（サイズ上限との競合時は安全窓優先）。【変更: 枠のみ→相談結果で確定。安全窓の追加を含む】
4. 移行の原子性: 書き込み順を「シャード本体→所在一覧→ホット index」に固定し、途中で止まっても「エントリがどこにも無い」状態を作らない（最悪でも二重に存在する側に倒す。二重存在はマージ修理が吸収できる）。冪等な再実行で収束させる。変更なし（当初案を維持）。
5. リポジトリ総量: 当初は今回の計画に別リポジトリ化まで含める案だったが、期限の圧力は index 側にあり、総量側は 1GB まで余裕がある。リスクの集中を避け、第2段階として発動条件（700MB）つきに分離した。ただし所在一覧にシャードごとの所在を持たせる先行設計で、将来の移行を安くする。
6. Git Data API: 前回監査の勧告だが、これは Contents API の 1MB という天井を外すだけで、「1 つのファイルが伸び続ける」構造は残る。フックの読み取りも大きなファイルの丸ごと取得になり、毎回の転送量が増え続ける。主対策としては不採用とし、シャード化（小さいファイルの追加のみ）で API 自体を変えずに済ませる。
7. 閾値アラート: 単体では解決にならないが、ロールオフ不全の検出と第2段階の発動検知として併設する。宛先は総合、経路は watchdog の定期報告に相乗りさせる（新しい常駐の仕組みは作らない）。変更なし。
8. エントリ削減: uploaded_at を落としても 1 件あたり約15%しか減らず、期限は数日しか延びない。シャード化の前では意味が薄く、不採用。変更なし。
9. （追加ラウンドで浮上）シャードの粒度: 当初案は月別だったが、実測ペースでは 1 か月分が約1.1MB となり、シャード自体が上限を超える。サイズで閉じる方式（500KB を超えない）に変更し、月別は命名の目安に留める。
10. （追加ラウンドで浮上）移行の実行主体: Mac 側の serve.py が起動時に行う前例方式を採る。手作業の移行スクリプトを別に作ると、ユーザーの Mac での実行手順が増え、検証も弱くなるため。変更なし（前例踏襲を確認）。

計画レベルで論点は出尽くしたと判断する。残る数値（上限 400KB、シャード 500KB、発動値 700MB）は第0ステップの実測で裏付ける前提の仮置きである。

## 監査指示の具体化案（発動はユーザーの判断）

- 対象: 第1〜第4ステップの実施期間。
- 開始点: 実装指示が全管轄に到達した時点。実行間隔: 実施中は毎日 00時回の定期監査に相乗りし、加えて各ステップの完了報告のたびに照合する。
- 初回の扱い: 第1ステップ（移行）の完了報告を受けた時点を初回照合とする。
- 照合項目: (a) リポジトリ上の所在一覧＋全シャードのエントリ総数が、移行前の実測（983 件＋その後の増加分）と一致すること。(b) ホット index の実サイズが上限以下であること。(c) 固定事項 1〜8 への適合（コードと実物での照合）。(d) 二重送信が起きていないこと（到着報告と送信済み記録の突合）。
- 停滞の判定: 24時間を超えて小報告が無い場合を停滞とする。ただし「ユーザーの対応待ちである旨の報告が出ている場合」は停滞としない（沈黙だけを停滞とする）。
- 逸脱の格付け: 違反／リスク／観察の 3 段階。権限は読み取り専用で、差し止めはしない（問題があれば総合とユーザーへ上げる）。
- 終了条件: 第4ステップの完了報告と最終照合が済み、大報告が出た時点で終了する。
