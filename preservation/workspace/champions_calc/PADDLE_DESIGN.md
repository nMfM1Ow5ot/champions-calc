# PaddleOCR 補助チャンネル化 設計文書 (ステップ0)

委任: 質問・調査チャット (f0e37323)、ユーザーの明示指示による。
主担当: バックエンド (919e769f)。相談先: 画像認識 (378dd179、ステップ0)。
監視: 監査 (706c9700、期間限定)。計画は たたき台+自己議論3ラウンド
(論点16件) を経た確定版。本書は固定事項の記録であり、ステップ0で
確定する数値 (モデル・余白・拡大率) を追記して完了とする。

## 目的と範囲
- PaddleOCR を Vision の補助チャンネルとして併走させ、読みを証拠
  として記録する。状態の決定には一切使わない (読みの照合判定への
  使用も本範囲外)。見せ合いの種族同定は対象外。
- 方式A: Mac 上に Python の PaddleOCR 常駐サイドカーを置き、reader が
  必要な切り出し (プレート、メッセージ帯。全画面は見せ合いの確定時
  などフレームを絞った場面のみ) だけを渡す。

## 固定事項 (委任より)
- 版: paddleocr 3.7.0 / paddlepaddle 3.3.1 に固定。
  enable_mkldnn=False。傾き分類・歪み補正・行方向の各段は無効化。
- 受け渡し: ファイル経由の上限付き列。reader が要求一覧 (JSONL) を
  追記し、切り出し画像は回転リングで渡す。要求には元フレーム、
  切り出し位置 (余白込み)、種別、フレーム番号、撮影時刻を含める。
  処理済みの切り出しはサイドカーが消し、滞留で捨てた分は件数を
  記録する。reader はサイドカーを一切待たない。
- 投入の対象: obs にプレート/読み取りの記録が出たフレームに限る。
  切り出しの内容が前回と同一なら送らない (重複除去)。デバッグ記録が
  発火した瞬間のフレームは優先投入する。
- 証拠の形式: 別ファイル battle_<試合キー>_paddle.jsonl。各行に
  フレーム番号と撮影時刻 (obs との突き合わせキー)、obs の pass 名と
  一致する領域名、モデル名と版を必須とする。記録は Paddle の生出力
  (ボックスごとの文字列と信頼度) のまま無加工。記録時点での足切りや
  正規化は行わない。切り出し画像そのものは残さない。
- 配送: serve.py に _obs.jsonl と同様の接尾辞扱いを追加する。到着側の
  分類 (fetch_battle_logs.py への paddle カテゴリ追加) は質問・調査
  チャット側で対応 (調整済みとして扱う)。
- 起動と監督: サイドカーは reader が起動・監督し、心拍を持つ。
  reader の再起動時は心拍ファイルで既存のサイドカーを引き継ぎ、
  心拍が死んでいる場合だけ掃除して立て直す (単一インスタンス保証)。
  試合ごとにサイドカーを立て直す。PaddleOCR が無い環境では「証拠が
  欠けるだけ」の縮退状態とし、通知は1回だけ、再試行は長い間隔にする。
- 試合の区切り: 試合終了時に最大で約10秒だけ残りの処理を待ち、
  残った分は未処理の件数として証拠ファイルの末尾に記録して締める。
- 負荷の制限: サイドカーは低い優先度で動かし、Paddle のスレッド数に
  上限を付ける。要求が滞留したら積極的に捨てる。
- 無効化: 起動フラグまたは設定で供給側を丸ごと無効化できるスイッチ
  を用意し、無効化しても reader の他の動作は従来どおりとする。
- 可視化: 試合ごとに「要求した件数・結果が返った件数・捨てた件数」
  を reader が記録し、ログ到着時の報告で証拠の件数が見えるようにする。
- モデルと環境: 既定は small。モデルと仮想環境は Mac のローカルに
  のみ置き、同期対象や ZIP には含めない。導入は再実行可能な
  スクリプトと手順書の形で用意する。

## ステップ0で確定する数値
画像認識 (378dd179) への相談結果 (2026-11-23) を反映した。
- 切り出しの基準領域: obs に記録された領域と同一にする (証拠が
  「同じ領域に対する Vision の読み」と対で残ることが照合の前提)。
  余白は基準領域の外側に足し、証拠には基準領域と余白込みの
  切り出し範囲の両方を記録する。
  - プレート: 縦 ±0.010 H、横 ±0.006 W (横は隣のプレートと領域が
    重なるため控えめに。余白の主目的は端の文字行を内側に入れること)
  - メッセージ帯: 基準は [0, 0.66, 1, 1]。余白は上側のみ、開始を
    0.65 まで広げる (1行目が上端に張り付く場面の対策)。左右・下は
    追加しない
- 拡大率: 等倍が実証済みの基準。プレートのみ 1倍/2倍を Mac 実測で
  比較し、検出漏れの改善が確認できれば 2 倍を採用する。帯は等倍。
- モデル: small / medium (確定条件: medium は1件あたり約2秒以内で
  名前の読みが明確に上回る場合のみ許容)。「名前の読み」の判定は
  完全一致ではなく、種族名・持ち物名として辞書で復元できるかで
  数える (濁点崩れはモデル規模では解消しない)。2秒の予算は帯と
  プレートで分けて測る。VM 試行では質の差は実感できず、small が
  約5倍速かった。
- 投入する pass の範囲 (相談結果):
  - plate:mineA/mineB/oppA/oppB: 最優先。ただし obs の plate pass は
    固定領域フォールバック時にしか出ないため件数は少なめ (既知の
    特性として記録する)
  - boxes のメッセージ帯: 優先度は高い
  - boxes の全画面: 見せ合い・マッチング画面やデバッグ発火時点
    など場面を絞った場合のみ
  - boxes の上部帯 [0, 0, 1, 0.1]: 低優先 (余力があれば)
  - hpbar / decode: 投入対象から外す (切り出し画像が存在しない)
- 上記の値 (余白・拡大率・モデル) は要求の記録に残す (証拠の
  再現可能性のため)。

## ステップ0の確定値 (2026-11-23、Mac 実測に基づく)
実測: paddle_kit の実切り出し28件 (プレート18件+帯10件、難所の
相手プレート6件を含む) を Mac で両モデル計測 (measure_result.jsonl)。
中央値: small = プレート等倍 71ms / 2倍 241ms、帯 878ms。
medium = プレート等倍 260ms / 2倍 1022ms、帯 3617ms。
名前の復元可否 (辞書照合、濁点折り畳み込み): プレート等倍で
small・medium とも 6/18 (33%) で同等。small の2倍は 5/18 と悪化し、
検出ボックス数も減った (1.9→1.4)。
- モデル: **small** に確定。medium は帯の中央値 3617ms が予算
  (約2秒) を超え、名前の読みでも明確な優位が無かった。
- 拡大率: **等倍** に確定 (プレートの2倍は改善なし)。
- 余白: 相談結果どおり (プレート縦 ±0.010 H / 横 ±0.006 W、帯は
  上側のみ開始 0.65)。
- 参考: 1フレーム分 (プレート4件+帯1件) のサイドカー処理は
  合計で約1.2秒が目安。供給側は重複除去と上限付き列で吸収する。
ステップ0はこれで完了とする。

## ステップ1の設計判断 (自己議論の結論)
- スプールの置き場所: ~/champions_paddle/spool/ (Mac ローカル)。
  プロジェクトの logs/ には完成した証拠ファイルだけが入り、書き手は
  reader に一元化する (サイドカーは logs/ に書かない。撮影と認識の
  独立化で確立した「ログを書くのは1か所」の原則の延長)。
- 証拠の組み立て: サイドカーは結果 (results.jsonl) をスプールに
  返し、reader が battle_<試合キー>_paddle.jsonl へ整形して書く。
- 結果の対応付け: 要求ごとに通し番号 (reqid) を付け、サイドカーは
  全ての要求に done / dropped のどちらかの結果を返す。試合終了時の
  締めで 未処理 = 要求 - 返却 - 破棄 として数える。
- 切り出しの作り方: ocr / ocrBoxes の出口 (obs 記録と同じ箇所) で
  供給する。CGImage の cropping は左上原点で画素座標に直し、
  JPEG 化はデバッグ撮影と同じ NSBitmapImageRep (品質 0.85) を使う。
  切り出しと書き出しは専用の直列キューで行い、認識ループは
  依頼を積むだけにする。
- 重複除去: 切り出し JPEG のハッシュを pass+領域ごとに前回と比較
  し、同一なら送らない。
- 優先投入: デバッグ記録が発火したフレーム (obsFrameSeq が一致)
  の要求に優先印を付け、全画面の boxes は優先印のあるフレームに
  限る (相談結果の「場面を絞る」への対応)。
- 試合終了時の締め: archiveCurrentBattle から供給キュー上の
  非同期処理として行う (最大約10秒の吸い上げ→締め行の記録→
  サイドカー終了)。認識ループはブロックしない。次の試合の開始
  処理も同じ直列キューに積むため、締めと再起動の順序が保たれる。
- 監督: 心拍ファイル (heartbeat.json、pid・試合キー・状態・
  モデル名) をサイドカーが約2秒ごとに更新する。reader は認識
  ループで心拍の鮮度を確認し、45秒を超えて古ければ再起動を試みる
  (多発防止に間隔を空ける)。reader の起動時は、心拍が新しく pid が
  生きていれば既存のサイドカーを引き継ぎ、二重起動を避ける。
- 利用不可の縮退: venv の python やモデルの読み込みに失敗したら
  心拍に unavailable を残してサイドカーは終了する。reader は
  実行中に1回だけ通知し、再試行は30分以上の間隔を空ける。
- 無効化スイッチ: 起動引数 --no-paddle、環境変数
  CHAMPIONS_PADDLE_OFF=1、ファイル ~/champions_paddle/DISABLED の
  いずれかで供給側を丸ごと無効化する。
- スレッド数と優先度: nice -n 10 で起動する。スレッド数の上限は
  当初 OMP_NUM_THREADS 等の環境変数で付けたが、ステップ2の実機で
  paddle のネイティブなスレッドプール内 (EventCount::Park で待機中
  のワーカースレッド) の SIGSEGV が発生し、上限なしで安定していた
  ステップ0実測との差分として最有力の容疑となったため、環境変数
  による上限は撤去した (2026-11-23、reader build 20261123_0337)。
  負荷の制御は nice と供給側の間引き・全体上限が担う。スレッド
  上限の再導入は、単独の変更として実測を経てから行う。
